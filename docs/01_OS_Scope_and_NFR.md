# Границы операционной системы

## 1.Ч то входит в границы ОС

Основной акцент проекта сделан на файловой подсистеме, поэтому
именно операции с файлами и каталогами реализуются в полном объёме.
Остальные подсистемы присутствуют как вспомогательные.

### 1.1. Файловая система на SQLite (ядро проекта)

- Хранение файлов и каталогов в базе данных SQLite — единое
  хранилище, где каждая запись описывает файл или каталог.
- Иерархия каталогов — древовидная структура, родительские и
  дочерние узлы, пути (абсолютные и относительные).
- Операции с файлами:
  - создание (`create`), чтение (`read`), запись (`write`),
  - удаление (`delete`), переименование (`rename`),
  - копирование (`copy`), перемещение (`move`).
- Операции с каталогами:
  - создание (`mkdir`), удаление (`rmdir`),
  - листинг содержимого (`ls`/`dir`),
  - навигация (`cd`), получение текущего пути (`pwd`).
- Метаданные файлов — размер, дата создания и изменения,
  владелец, права доступа.
- Транзакционность — использование возможностей SQLite для
  атомарности операций (частичное выполнение не допускается).

### 1.2. Разграничение прав пользователей (применительно к ФС)

- Учёт пользователей — локальный список пользователей и групп.
- Права доступа к файлам и каталогам — чтение/запись/выполнение
  для владельца, группы и остальных (аналог rwx).
- Проверка прав при каждой операции с файлом или каталогом.
- Смена владельца и прав (`chmod`, `chown` в упрощённом виде).

### 1.3. Командная оболочка

- Интерпретация команд пользователя, связанных с файловой
  системой: `ls`, `cd`, `mkdir`, `rm`, `cp`, `mv`, `cat`, `echo >`.
- Встроенные команды для работы с пользователями: `whoami`,
  `su` (упрощённо), `chmod`, `chown`.
- Запуск внешних программ — базовая поддержка, без сложного
  управления заданиями.

### 1.4. Вспомогательные подсистемы (в минимальном объёме)

- Управление процессами — только в объёме, необходимом для
  работы оболочки: создание процесса под команду, ожидание
  завершения.
- Управление памятью — не реализуется как отдельная подсистема;
  используется память, предоставляемая средой выполнения Python.

## 2. Что НЕ входит в границы ОС

Следующие функции не реализуются, а лишь имитируются или опускаются
сознательно.

- Работа с реальным аппаратным обеспечением.
  *Обоснование:* прямая работа с диском, контроллерами и шинами
  требует драйверов и привилегий ядра. В учебной ОС файлы хранятся
  в SQLite, а не на «сыром» носителе.

- Поддержка прерываний и драйверов.
  *Обоснование:* реализация обработчиков прерываний и модели
  драйверов — отдельная крупная тема, не связанная с файловой
  системой, и не помещается в отведённое время.

- Реальная блочная адресация и журналирование на уровне носителя.
  *Обоснование:* за это отвечает SQLite; собственная реализация
  блоков, inode и журнала избыточна для демонстрации принципов ФС.

- Сетевая файловая система (NFS, SMB) и сетевые протоколы.
  *Обоснование:* требует сетевого стека и выходит за рамки темы;
  файловая система локальная.

- Интеграция с внешними службами каталогов (LDAP, Active Directory).
  *Обоснование:* пользователи хранятся локально в той же БД;
  интеграция с внешними каталогами — отдельная задача.

- Графический интерфейс.
  *Обоснование:* GUI не является темой проекта; взаимодействие
  ведётся через командную оболочку.

- Полноценное управление процессами и планирование.
  *Обоснование:* это не тема проекта; процессы поддерживаются
  ровно настолько, чтобы работала оболочка.

- Полноценная виртуальная память и подкачка.
  *Обоснование:* не относится к файловой системе; используется
  память среды выполнения.

## 3. Вывод

Границы проекта очерчены вокруг файловой системы на SQLite:
операции с файлами и каталогами, права доступа и командная оболочка
реализуются полностью, а аппаратные, сетевые и графические аспекты
сознательно исключены. Такой подход позволяет сосредоточиться на
действительно важных деталях и уложиться в отведённое время.



# Сценарии использования

## Роли

- Обычный пользователь — ограниченные права, может работать с файлами только в своём каталоге.
- Администратор (суперпользователь) — полные права, управляет пользователями и системными настройками.
- Система — совокупность фоновых процессов (планировщик, сборщик мусора и т.п.).

## Сценарий 1. Копирование файла в другой каталог

- Действующее лицо: Обычный пользователь
- Последовательность системных вызовов:
  1. Пользователь вводит команду копирования с указанием источника и назначения.
  2. Оболочка вызывает `sys_copy(src, dst)`.
  3. Ядро проверяет права на чтение источника и на запись в целевой каталог.
  4. Ядро через модуль файловой системы читает запись источника из таблицы `files`.
  5. Модуль файловой системы создаёт новую запись в таблице `files` с новым путём.
  6. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`files`), `syscalls_log`.

## Сценарий 2. Переименование каталога

- Действующее лицо: Обычный пользователь
- Последовательность системных вызовов:
  1. Пользователь вводит команду переименования каталога.
  2. Оболочка вызывает `sys_rename(old_path, new_path)`.
  3. Ядро проверяет права на запись в родительский каталог.
  4. Модуль файловой системы обновляет поле имени в записи таблицы `files`.
  5. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`files`), `syscalls_log`.

## Сценарий 3. Смена владельца файла

- Действующее лицо: Администратор
- Последовательность системных вызовов:
  1. Администратор вводит команду смены владельца с указанием нового пользователя.
  2. Оболочка вызывает `sys_chown(path, new_owner)`.
  3. Ядро проверяет, что вызывающий обладает правами администратора.
  4. Модуль файловой системы обновляет поле владельца в записи таблицы `files`.
  5. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`files`), `syscalls_log`.

## Сценарий 4. Поиск файлов по маске

- Действующее лицо: Обычный пользователь
- Последовательность системных вызовов:
  1. Пользователь вводит команду поиска с указанием маски.
  2. Оболочка вызывает `sys_find(pattern)`.
  3. Ядро проверяет права на чтение каталогов, доступных пользователю.
  4. Модуль файловой системы выполняет выборку из таблицы `files` по маске.
  5. Найденные пути возвращаются оболочке для отображения.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`files`).

## Сценарий 5. Создание жёсткой ссылки

- Действующее лицо: Обычный пользователь
- Последовательность системных вызовов:
  1. Пользователь вводит команду создания ссылки с указанием файла и имени ссылки.
  2. Оболочка вызывает `sys_link(target, link_name)`.
  3. Ядро проверяет права на создание в целевом каталоге.
  4. Модуль файловой системы создаёт запись в таблице `files`, ссылающуюся на тот же блок данных.
  5. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`files`), `syscalls_log`.

## Сценарий 6. Блокировка файла для монопольного доступа

- Действующее лицо: Обычный пользователь
- Последовательность системных вызовов:
  1. Пользователь вводит команду блокировки файла.
  2. Оболочка вызывает `sys_lock(path)`.
  3. Ядро проверяет права на запись в файл.
  4. Модуль файловой системы устанавливает признак блокировки в записи таблицы `files`.
  5. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`files`), `syscalls_log`.

## Сценарий 7. Создание нового пользователя

- Действующее лицо: Администратор
- Последовательность системных вызовов:
  1. Администратор вводит команду создания пользователя с логином и паролем.
  2. Оболочка вызывает `sys_useradd(login, password)`.
  3. Ядро проверяет права администратора.
  4. Модуль аутентификации вычисляет хэш пароля.
  5. Модуль файловой системы создаёт запись в таблице `users`.
  6. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль аутентификации, модуль прав доступа, SQLite (`users`), `syscalls_log`.

## Сценарий 8. Удаление учётной записи пользователя

- Действующее лицо: Администратор
- Последовательность системных вызовов:
  1. Администратор вводит команду удаления пользователя.
  2. Оболочка вызывает `sys_userdel(login)`.
  3. Ядро проверяет права администратора.
  4. Модуль файловой системы удаляет запись из таблицы `users`.
  5. Модуль файловой системы переназначает владение файлами удалённого пользователя.
  6. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`users`, `files`), `syscalls_log`.

## Сценарий 9. Очистка удалённых записей (сборщик мусора)

- Действующее лицо: Система
- Последовательность системных вызовов:
  1. Сборщик мусора запускается по таймеру.
  2. Ядро вызывает `sys_gc()`.
  3. Модуль файловой системы выбирает из таблицы `files` записи с признаком «удалён».
  4. Модуль файловой системы удаляет эти записи безвозвратно.
  5. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: ядро, сборщик мусора, модуль файловой системы, SQLite (`files`), `syscalls_log`.

## Сценарий 10. Резервное копирование файловой системы

- Действующее лицо: Администратор
- Последовательность системных вызовов:
  1. Администратор вводит команду резервного копирования.
  2. Оболочка вызывает `sys_backup(dest)`.
  3. Ядро проверяет права администратора.
  4. Модуль файловой системы формирует снимок таблиц `files` и `users`.
  5. Снимок сохраняется в указанный файл базы данных SQLite.
  6. Ядро фиксирует операцию в `syscalls_log`.
- Задействованные модули: командная оболочка, ядро, модуль прав доступа, модуль файловой системы, SQLite (`files`, `users`), `syscalls_log`.



# Нефункциональные требования

## 1. Требования производительности

Максимальное время обработки одного системного вызова не должно превышать
50 миллисекунд. Способ проверки: замер с помощью функции `perf_counter`
из модуля `time` стандартной библиотеки Python вокруг вызова.

Система должна одновременно выдерживать не менее 10 процессов.
Способ проверки: запустить 10 процессов и убедиться, что все они
зарегистрированы в таблице `processes` и не завершились аварийно.

Дополнительно, с учётом темы проекта — файловой системы на SQLite:

Максимальное время выполнения файловой операции (создание, чтение,
запись, удаление) не должно превышать 30 миллисекунд для файла
размером до 1 МБ. Способ проверки: замер `perf_counter` вокруг вызова,
повтор 100 раз, берётся среднее и максимальное значение.

Поиск файла по маске в каталоге, содержащем 1000 записей, должен
занимать не более 100 миллисекунд. Способ проверки: замер времени
выполнения `sys_find` на заранее подготовленном каталоге.

Время открытия соединения с базой данных SQLite не должно превышать
20 миллисекунд. Способ проверки: замер `perf_counter` до и после
вызова `sqlite3.connect()`.

## 2. Требования надёжности

При возникновении ошибки в пользовательском процессе ядро обязано
перехватывать исключения и не завершаться аварийно. Вместо этого процесс
должен быть остановлен с записью соответствующего сообщения в журнал.
Способ проверки: намеренно вызвать исключение в процессе, убедиться,
что ядро продолжает работу, процесс остановлен, а запись в `syscalls_log`
присутствует.

При попытке выделения памяти сверх установленного лимита система должна
возвращать ошибку и не изменять своё состояние. Способ проверки:
запросить память выше лимита и убедиться, что вернулась ошибка, а
таблицы `processes` и учёт памяти не изменились.

Дополнительно, с учётом темы проекта:

Операции с файлами должны быть атомарными: при сбое на середине операции
состояние таблицы `files` не должно меняться. Способ проверки:
имитировать сбой внутри транзакции и проверить, что запись осталась в
исходном виде.

При повреждении базы данных SQLite система должна сообщать об ошибке и
не продолжать работу с повреждёнными данными. Способ проверки: открыть
заведомо повреждённый файл БД и убедиться в корректной обработке
исключения.

Все критические операции должны логироваться до их выполнения и после —
чтобы при сбое можно было восстановить ход событий. Способ проверки:
имитировать сбой и убедиться, что в `syscalls_log` присутствуют обе
записи для одной операции.

## 3. Требования безопасности

Все пароли должны храниться исключительно в виде хэша, полученного с
помощью алгоритма SHA-256. Способ проверки: открыть таблицу `users`
и убедиться, что в поле пароля хранится 64-символьная hex-строка, а не
открытый текст.

Обычный пользователь не должен иметь возможности удалять или изменять
файлы, принадлежащие администратору. Способ проверки: попытаться
выполнить `sys_unlink` или `sys_write` от имени обычного пользователя
над файлом администратора — ожидается отказ.

Все системные вызовы должны фиксироваться в журнале с указанием имени
вызова, аргументов, пользователя и результата. Способ проверки:
выполнить несколько вызовов и проверить наличие всех четырёх полей в
`syscalls_log`.

Дополнительно, с учётом темы проекта:

Смена владельца файла (`sys_chown`) должна быть доступна только
администратору. Способ проверки: попытаться выполнить `sys_chown` от
имени обычного пользователя — ожидается отказ с записью в журнал.

Блокировка файла (`sys_lock`) должна сниматься автоматически при
завершении процесса-владельца. Способ проверки: заблокировать файл,
завершить процесс и убедиться, что признак блокировки снят.

Резервная копия (`sys_backup`) должна создаваться только по команде
администратора и сохраняться в защищённый каталог. Способ проверки:
попытаться выполнить `sys_backup` от имени обычного пользователя —
ожидается отказ.

## 4. Требования поддерживаемости

Исходный код должен быть разбит на модули, каждый из которых отвечает
за строго определённую задачу. Способ проверки: просмотр структуры
проекта — отдельные модули для ядра, файловой системы, аутентификации,
прав доступа, журнала и командной оболочки.

Рекомендуемый размер одного модуля не должен превышать 300 строк.
Способ проверки: подсчёт строк командой `wc -l` по каждому файлу `.py`.

Дополнительно, с учётом темы проекта:

Каждый модуль должен иметь docstring с описанием назначения и публичных
функций. Способ проверки: наличие docstring в начале файла и у каждой
публичной функции.

Публичные функции должны иметь аннотации типов. Способ проверки:
просмотр кода, при необходимости — проверка с помощью `mypy`.

Все модули должны быть покрыты unit-тестами не менее чем на 70% по
строкам. Способ проверки: запуск `pytest --cov`, порог 70%.

## 5. Требования ресурсоёмкости

Операционная система должна работать на стандартном Python версии
3.10 и выше без необходимости установки дополнительных серверов баз
данных или специализированного программного обеспечения. Способ
проверки: запуск на «чистом» Python 3.10+, где используется только
стандартная библиотека и модуль `sqlite3`.

Дополнительно, с учётом темы проекта:

Объём оперативной памяти, занимаемой ядром и оболочкой, не должен
превышать 100 МБ при 10 процессах. Способ проверки: замер через
`tracemalloc` или `psutil`.

Размер файла базы данных SQLite при 1000 файлах и 10 пользователях не
должен превышать 50 МБ. Способ проверки: измерить размер файла БД
после наполнения.

Запуск системы и инициализация базы данных должны занимать не более
