# Ответы на контрольные вопросы

## 1. Чем Scrum отличается от Kanban?

Scrum работает спринтами — фиксированными отрезками по 1–4 недели. Есть роли (Scrum Master, Product Owner), обязательные встречи и Sprint Backlog. Задачи внутри спринта менять нельзя.

Kanban — это непрерывный поток без спринтов. Ролей нет, встречи не обязательны, задачи берутся по мере освобождения. Можно добавлять новые задачи в любой момент.

## 2. Что такое User Story и критерии приёмки?

User Story — это требование, описанное с точки зрения пользователя. Шаблон: «Как <роль>, я хочу <действие>, чтобы <цель>». Например: «Как менеджер, я хочу видеть товары с низким остатком, чтобы вовремя заказать новую партию».

Критерии приёмки — конкретные условия, при которых история считается выполненной. Например: «Отображаются товары с остатком ≤ 3», «Список отсортирован по возрастанию». Они нужны, чтобы разработчик и заказчик одинаково понимали, что значит «сделано».

## 3. Зачем нужна оценка задач в Story Points?

Story Points (SP) — условная мера сложности задачи, а не времени. Нужна, чтобы:

- планировать спринт — сколько задач влезет;
- сравнивать задачи — какая тяжелее;
- считать скорость команды (сколько SP за спринт);
- не зависеть от часов, которые обманывают.

Шкала: 1 — просто, 2 — чуть сложнее, 3 — средне, 5 — сложно, 8 — очень сложно.

## 4. Что такое WIP-лимит и зачем он нужен?

WIP (Work in Progress) — ограничение на количество задач в работе одновременно. Например: в колонке In Progress — не более 2 задач.

Он нужен, чтобы не распылять внимание, быстрее закрывать задачи, видеть узкие места, меньше переключений. Закончил одну задачу — берёшь следующую, а не начинаешь новую параллельно.

## 5. Какие три вопроса задаются на Daily Standup?

1. Что сделано с прошлого стендапа?
2. Что планируется сделать сегодня?
3. Какие есть препятствия?

Встреча короткая (5–15 минут), все стоят, каждый отвечает по очереди. Цель — синхронизация, а не отчёт.

## 6. Что такое ретроспектива и какие вопросы на ней обсуждаются?

Ретроспектива — встреча в конце спринта, где команда анализирует процесс, а не продукт. Обсуждают три вопроса:

1. Что прошло хорошо?
2. Что можно улучшить?
3. Что попробуем в следующем спринте?

Результат — 2–3 конкретных действия на следующий спринт. Например: «делать коммит после каждой задачи, не откладывать».




# Ответы на контрольные вопросы (занятие №7)

## 1. Чем main отличается от develop в Git Flow?

main — это стабильная версия продукта. В неё попадает только проверенный код, готовый к использованию. Из main делаются релизы.

develop — это ветка для интеграции новых функций. Все feature-ветки сливаются сначала в develop, где код тестируется и проверяется. Когда набирается достаточно изменений, develop сливается в main.

Коротко: main — для пользователей, develop — для разработчиков.

## 2. Зачем нужны feature-ветки?

Feature-ветки нужны, чтобы разрабатывать каждую функцию изолированно. Пока работа идёт в отдельной ветке, основная ветка (main или develop) остаётся стабильной.

Преимущества:

- можно делать эксперименты, не ломая рабочий код;
- несколько функций разрабатываются параллельно;
- если функция не удалась, её легко отбросить — просто не сливать ветку;
- изменения проще проверить и откатить.

## 3. Что такое конфликт слияния и как его разрешить?

Конфликт слияния возникает, когда две ветки изменяют один и тот же участок одного файла. Git не может автоматически определить, какую версию оставить, и оставляет в файле специальные маркеры:

    <<<<<<< HEAD
    (версия из текущей ветки)
    =======
    (версия из сливаемой ветки)
    >>>>>>> имя-ветки

Как разрешить:

1. Открыть файл с конфликтом в редакторе.
2. Выбрать правильную версию или объединить обе.
3. Удалить маркеры конфликта.
4. Сохранить файл.
5. Выполнить git add <файл>.
6. Завершить слияние командой git commit.

В VS Code можно нажать кнопку «Принять текущее», «Принять входящее» или «Принять оба изменения» — тогда маркеры удалятся автоматически.

## 4. Что такое hotfix и когда он используется?

Hotfix — это срочное исправление критической ошибки в стабильной версии продукта (в ветке main).

Используется, когда:

- в main обнаружена ошибка, которая мешает работе;
- исправление нужно срочно, до следующего релиза;
- ждать, пока develop накопит изменения, нельзя.

Особенности hotfix:

- создаётся от main, а не от develop;
- после исправления сливается и в main, и в develop, чтобы фикс не потерялся;
- после слияния ветка hotfix удаляется.

## 5. Зачем нужен Pull Request?

Pull Request (PR) — это запрос на слияние изменений из одной ветки в другую. Используется в командной работе.

Зачем нужен:

- чтобы изменения проверил другой разработчик перед слиянием;
- чтобы обсудить код и оставить комментарии;
- чтобы запустить автоматические тесты (CI);
- чтобы вести историю: кто, что и когда предложил.

В учебном проекте PR можно имитировать — описать его в Markdown-файле: что сделано, как проверить, какие задачи связаны.

## 6. Как посмотреть граф истории коммитов?

Команда:

    git log --oneline --graph --all

Что делают флаги:

- --oneline — каждая запись в одну строку;
- --graph — рисует граф ветвления символами * и |;
- --all — показывает все ветки, а не только текущую.

Пример вывода:

    * 447735f (HEAD -> develop) Разрешён конфликт
    |\
    | * 564a6e6 Hotfix: исправлена функция cart_total
    * | 843107b Добавлено описание разрешения конфликта
    |/
    * 125374a US-1: добавлена функция get_low_stock

Граф наглядно показывает, какие ветки создавались, где сливались и где возникали конфликты.
